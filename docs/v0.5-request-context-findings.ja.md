# v0.5の要求コンテキスト比較

2026-11-03。元のv0.5設計や受入済み証跡を変更せず、次の要求比較に必要な条件を記録する。

## 既存比較に残っていた差

[旧native要求の入口](../experiments/wp-request-probe/prepare.py)はGETのstdinに秘密を含む比較用JSONを載せ、`CONTENT_TYPE=application/json`と本文長をCGIへ渡していた。owned fixtureはWordPressへ渡すURI・query・GETを設定し直すが、このContent-Typeと本文は残る。一方、[既存Wasm入口](../experiments/php-wasix-wp-request-probe/src/main.rs)はstdin EOF、`CONTENT_LENGTH=0`、Content-Typeなしである。

固定WPの`wp_is_json_request()`は`CONTENT_TYPE`と`HTTP_ACCEPT`を見る。`wp_debug_mode()`はJSON要求と判定すると`display_errors`を0へ設定する。したがって、既存の全HTML一致は、両入口のrequest contextまで一致した根拠にはならない。旧status APIの失敗と修正は[CGI報告](v0.5-cgi-status-line-findings.ja.md)のとおり保持する。

## 新しいnative比較基準

新しい独立profileでは、private configurationを所有ファイルから読み、実CGIのstdinは空にする。CGI用の有限queryは入口のためだけに使い、WP起動前に公開要求のURI・query・GET／POST／COOKIE／REQUESTを整える。Content-Type・Accept・認証情報を含め、今回の匿名GETに渡す条件と渡さない条件を固定する。設定ファイルは所有PHPRCで選び、CGIが無視し得るCLIの`-n`／`-d`へ依存しない。

比較対象には、全応答に加えて、WP起動前後の公開request snapshot、空の`php://input`、`wp_is_json_request()`と`display_errors`を含める。警告を出力補正で消さず、JSON wrapperは`header('Content-Type: application/json', true, 200)`で外側のstatusを設定する。内側のWP応答statusとは区別する。

公開ケースは匿名ホームと、存在しない投稿IDを指定する`/?p=2147483647`の404とする。既定のplain permalinkでは無作為なpathだけが404になるとは限らないため、元のquery処理で不在を判定できる要求を使う。独立したDB照会で対象IDが存在しないことを確かめ、WPの404判定やredirectを置換しない。

404は`is_404()`、status404、標準template-loader／wp_head／wp_footerの実行、redirectなしを要求する。同じ要求をfresh CGIで繰り返し、全status／header順序／HTML bytesの一致を確認する。既存の固定公開日時seedを使い、ヘッダー・HTML・Unicodeの正規化は行わない。

初回candidate `0bee0e5`は両DBで上記の全応答・反復404・正常清掃を通過したが、homeのC環境に`QUERY_STRING=rp_request=1`が残る除去漏れが見つかった。元の`passed: true`を改変せず保存し、このcandidateを要求contextの最終基準にはしない。修正source `afe8781`では環境queryも除去し、homeは未設定、missingは公開queryだけになることを3段階で記録・照合する。環境のmethod・URIも公開値との完全一致を要求する。

## 修正後の実測

[新しいnative基準](../experiments/wp-request-context-probe/README.ja.md#query分離後の両db基準)はsource `afe8781`の両DB実行で成立した。homeの全応答は従来基準とも一致し、status200・3 headers・69,399 B。missingは元WPで`is_404()`とstatus404・5 headers・58,177 Bとなり、両DBとfresh再実行で全応答が一致した。

3段階のsnapshotではhomeの環境queryが未設定、missingが公開queryのみとなった。実本文は空、元WP起動後のJSON要求判定はfalse、`display_errors`は1のままである。各3 CGIのEOF／reapと5所有filesの個別清掃、正常DB停止、元WP全sourceとPHP全78 filesの前後一致も確認した。初回のsource・原判定・JSON全bytesは別に保存し、修正後の成功で上書きしない。

[offline監査記録](../experiments/wp-request-context-probe/evidence/clean-context-offline-audit.json)は35 Git source blobsと固定初回証跡の5参照metadata、元backup、全6公開CGI wireとcleanup記録を照合した。これは公開証跡とsourceの対応を確かめたもので、private contextや実binary／archiveを再実行・再検証した主張ではない。

## 次のWasm接続で維持する境界

native基準が両DBで成立した後、独立したWasm候補へ同じ公開request snapshotと二つの応答を接続する。既存のDB actor・RPC・collector・source catalog・capture・module検証は維持し、共有DB modeを要求ケースのために広げない。private nonce・saltは専用contextから渡し、要求本文やHTTPヘッダーへ混ぜない。

moduleのcompileを共有しても、各要求はfresh PHP／WASI／actorで実行する。外側CGIのJSON status200と内側WPの200／404を区別し、完全な既知native応答と一致する前に未知のHTMLを公開しない。接続終了、actor join、EOF、元source不変と所有DBの正常清掃を各段階の受入条件に含める。HTTP listener・任意plugin・ログインや書込み要求までの互換確認は別の残件である。

## 2026-11-04のWasm比較結果

source `f9f1f61`の[両DB CI](../experiments/php-wasix-wp-request-context-probe/README.ja.md#同じ公開contextと404の実wasm受入)で、同じ公開contextとhome／404／fresh反復404が成立した。元installer・fresh readも再通過し、全5実行の公開観測を比較した。homeはstatus200・全3 headers・69,399 B、404はstatus404・全5 headers・58,177 Bで、全responseと3 snapshotが固定native基準に一致した。

home 145 RPC、404／再実行は各74 RPC。各要求を別host processで起動するためmodule compile数は要求3件で3回であり、module cacheの実証にはしない。元actor／RPC／collector／managed access／captureをそのまま読み取り再利用し、Linux58 unit・195 inputsと正常disconnect／actor終了／EOF／container清掃が通過した。各1,883 source bindingsと203 Git sourcesへの独立した取り込み照合も完了した。

これで旧native入口のprivate Content-Type等に起因する比較条件差を、この有限case群では解消した。次はRustのHTTP入口へ完成CGI応答を接続し、公開入力とprivate configurationの分離を実HTTPでも確認する。比較用JSON wrapperを公開サービスの応答契約として採用したという意味ではない。

## 実HTTPへ接続した結果

source `3c4dbf1`の[両DB HTTP試験](../experiments/php-wasix-wp-http-probe/README.ja.md#実http経由の両db受入)で、同じ公開contextのhome／404／fresh反復404が実socket経由でも一致した。HTTPへ返したのはworkerが完成させたWP応答のstatus・origin headers・bodyであり、比較用JSON envelopeはprivateのままである。固定7不正要求の事前拒否、workerの要求ごとのnonce生成、EOF／reap、serverの正常終了、所有DBの正常清掃を確認した。

各2,711 source bindings・215 Git sourcesと元commitを照合した。既存のcontext workerとnative比較契約は変更していないため、実行経路には固定期待値への依存が残る。次は別の独立workerでprivateな完了応答を抽出し、比較は検証adapterへ残す。期待値判定を単に削除して未知のHTMLを公開する変更にはしない。
