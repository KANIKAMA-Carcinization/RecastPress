# v0.5の実行ホスト候補と次の縦断試験

2026-11-04。元のv0.5設計を変更せず、P0の実行ホスト部分の観測とP1への準備をまとめる。製品runtimeの採用・配布許可・P0全項目の完了を宣言する文書ではない。

## 実行候補

次のP1縦断試験では、Linux x86_64のCranelift候補を先に使う。LLVMは比較対象として継続し、Wasmer LLVM compilerの独自利用条件を製品へ自動採用しない。

| 項目 | 固定した実物 |
| --- | --- |
| PHP | 8.5.12、source `f4bfae79d5c19028349082f707930cf0951d23b9` |
| PHP側変更 | 固定のFiber・CGI prefork拒否・managed accessの3patch |
| Rust host | Wasmer 7.2.0 / wasmer-wasix 0.702.0 / Cranelift |
| ABI | wasm32、standard EH、shared imported memory。PHP intは実測8B |
| build環境 | Ubuntu 24.04 x86_64、Rust 1.94.0、固定4ツールasset |
| request形 | CGI、完全応答の保持、compile済みModuleをcloneし要求ごとfresh WASI |
| Rust呼出し | private file transport。stdoutをRPCとしてdispatchしない |

Node.js・native PHPへのfallbackは使わない。通常PHPは比較用の基準であり、製品の要求実行経路にはしない。

## 揃った実行契約

| 契約 | 観測 |
| --- | --- |
| 基本PHP・例外・Fiber・pure WP hooks・IO | native基準を維持し、両backendの固定corpusで一致 |
| CGI | GET/Cookie、POST/raw body、404/2 Cookie/7B binaryが両backendで一致 |
| 権限 | readonlyの照会false・実write拒否・17B不変・Permission deniedが同時に一致 |
| host DB/cache呼出し | 同じ3patch CGIでprivate RPC4要求が両backend通過。固定DB行・要求local cacheのみ |
| 元wpdbと実DB | Craneliftの同じ3patch CGIからprivate file RPC・Rust所有接続を通り、MySQL/MariaDBの27 API観測と各34 RPCが固定native基準に一致。Linux16 unit・正常清掃も通過 |
| 異常要求 | incomplete RPCはPHP終了成功でも拒否。次の要求はfresh stateで正常回復 |
| 資源診断 | 両backendで256MiB actual cap・期待OOM・無cap対照、初期1億Wasm points・実Exhausted・正常回復を確認 |

元Git、source/tool/patch/moduleと生JSONの対応は[実行候補の記録](../experiments/php-wasix-managed-access-probe/README.ja.md)を参照する。清掃の根拠は固定caseでのshutdown、EOF、channel終了、memory recycle、typed Globalの保持・drop、owned hostの終了・reapの観測範囲に限る。全資源の即時回収、stack guard/free/reuse、RSS、hostcallの待機上限まで実証したとはしない。

## P1で最初に確認するもの

上流`wpdb`のprepare/get系・insert/update/delete・prefix等をPHP側に残し、所有`db.php`から要求専有のRust DB sessionへ接続する。RustへWP APIを大量移植しない。最初はキャッシュ・索引・binlog最適化を経路へ加えない。

[driver準備案](../experiments/wpdb-rpc-probe/README.ja.md)では、既存binlog実験で固定したmysql_async 0.37.1を縦断候補とする。既存editing DBのSQLx経路は維持する。SQLxのFOUND_ROWS/MULTI_STATEMENTS、SQL入力のUTF-8制約、raw metadata不足を結果値の補正で隠さず、必要な能力制御をdriverの実handshakeに反映する。

独立driverではMySQL 8.4.13／MariaDB 11.8.9のTLS有無4profileで各28ケース、元wpdbでは両DBの非TLSprofileで各27ケースを通過した。全profileで正常shutdown・全child reapを確認し、初回失敗も別記録に保持する。この段階ではdriverと比較基準を個別に確かめたものであり、後続の結合結果とは分けて保存している。

その後の[通常PHPの結合試験](../experiments/wpdb-bridge-probe/README.ja.md)を維持したまま、[php-wasmの結合試験](../experiments/php-wasix-wpdb-probe/README.ja.md)を追加した。後者のsource `2bea0da`では、同じ27ケース本文・adapterの業務ロジックを保ち、CGI入口とtransportを要求専有private FSへ変更して両DBを通過した。PHPへDB資格情報やnetworkを渡さず、拡張mysqliの存在とRust RPC用opaque handleを実検査する。製品のnative PHP fallbackは追加していない。

実証はASCII query/escape・列名metadataの固定corpusまでである。標準更新ヘルパー、非ASCII SQL、raw error、通常WP bootstrap、TLS、製品ABIの不足を[次の実装順](v0.5-wp-bootstrap-plan.ja.md)に沿って補完する。固定ケースの成功を全wpdb互換と扱わない。

標準更新ヘルパーは[別の15ケース](../experiments/wpdb-crud-probe/README.ja.md)を追加した後、[同じcorpusをphp-wasmへ接続](../experiments/php-wasix-wpdb-probe/README.ja.md)した。source `60b4e5d`の両DB CIで全観測・公開16 SQL・40 RPC・正常清掃がnative基準に一致し、元27ケースとLinux20 unitも再通過した。元wpdbのschema照会とformat処理を維持した固定比較であり、通常WP bootstrap・全wpdb互換とは別の到達点である。

最初の比較は、同じ使い捨てMySQL/MariaDBの同じデータで行うnative実wpdbとRust bridgeの小さな縦断にする。SQL/値のbytes、NULL・empty・binary・decimal・big integer、0行metadata、同値UPDATEの0、insert_id・error後状態、transaction/rollbackと次要求の状態分離を含める。native `mysqli` handle/resultへの直接依存は、元A案の拒否対象のままである。

P0は元設計3.1の実行・版・依存・基準・policy・再利用判断を整理する段階であり、三環境はP0で成立候補、P7で正式受入となる。現在の独立hostの絶対workspace参照は、製品の配布経路としては使わない。P1のruntime入力配置と配布時のportable preflightを具体化し、正式運用・配布条件の残件を維持する。

## 配置を分離する次の実装

最初に、Rust HTTPアダプターとworkerを同じRPリリースの配置から起動できるようにする。現行実験は `CARGO_MANIFEST_DIR` からリポジトリへ戻り、CIのbuild receipt、`target/` のPHP-Wasm、準備済みWordPress catalogと実験用PHPを読む。配布側ではリリースの検証済みmanifestに実行ファイル、Wasm、WordPress catalog、本体所有のPHPの役割とバイト数・SHAを結び付ける。固定の配置内パスを使い、親とworkerが同じリリースを検証してからREADYを出す。

この段階では1サイト、loopback、固定3要求、所有DBの比較条件を保つ。リリースを別ディレクトリへ配置し、リポジトリ外の作業ディレクトリから同じ応答を得る。欠落、内容差し替え、別版の混在、symlinkによる配置外参照を待受前に拒否する。manifestのハッシュを検証済みの配布情報と照合し、一致した場合だけ起動へ進む。

その後に公開オリジン、WordPress設定、Rust DB接続先を一組のサイト設定として通す。公開オリジンはHTTPのHost検査とWP側のURL生成で共有し、DB資格情報はRust actorに渡す。外部拡張を有効化する前に、RP所有のdrop-in、標準wpdb経路、DB変更追跡に対する衝突を判定する。応答キャッシュは通常のWP実行と変更追跡が成立した段階で接続する。

配置検証の入口は `recastpress check-wordpress-release <directory> <manifest-sha256>` とする。呼び出し元が信頼するmanifestのSHAを渡す。CLIは2実行ファイル、PHP-Wasm、本体所有PHP7件、WordPressのsource manifestと全ツリーを照合し、検証結果だけをJSONで返す。検証用配置はLinuxの固定候補から作成し、別ディレクトリからの照合と、欠落・改変・配置外参照・追加drop-inの拒否を試験する。実行ファイルの起動とHTTP応答の再比較は、親とworkerがこの配置を読む段階で行う。[配置検証のCI](../.github/workflows/wordpress-preview-release.yml)

配置から起動する候補は、受入済みのRust HTTPとworkerを固定ソースから派生させる。`recastpress preview-wordpress <directory> <manifest-sha256> <capture-directory>` はLinuxの実験用入口であり、配置を検証してから同じPIDでHTTPアダプターに移る。両方に同じ配置ディレクトリとmanifestのSHAを渡し、実行中の自分が配置内の実行ファイルであることを検査する。WordPressとPHP-Wasmは配置から読み、DB設定はprivate stdinで渡し、captureは別の所有ディレクトリに作る。Linux CIでは配置の作成後に別名へ移し、リポジトリ外の作業ディレクトリから起動する。MySQLとMariaDBで各3応答・7拒否・要求ごとのDB状態・終了を比較する。[実行比較](../scripts/check_wordpress_preview_runtime.py)

source `619fd46`のLinux配置検証が通過した。実成果物から作った配置を移動し、リポジトリ外の作業ディレクトリから11ファイルとWordPressの3,782ファイル・467ディレクトリを照合した。既存配置への上書き、manifestのSHA不一致・重複キー、所有PHPの改変・欠落・リンク、追加drop-inの7ケースを拒否した。このCIの受入範囲は配置検証である。[CI証跡](../evidence/wordpress-preview-release/ci-42487489714/provenance.json)
