# RP開発者向け：診断CGIの既存status lineとJSON wrapper

2026-11-03。対象はv0.5の独立実験。元WordPress、テーマ、PHP moduleの3patchは変更しない。外部への報告送信はしていない。

## 観測

固定WordPressの匿名ホームは、マウント内の重複区切りの解釈修正後、両DBでstatus 200・全3header・HTML 69,399 Bがnativeと完全一致した。しかし[CI 41621939824](https://github.com/KANIKAMA-Carcinization/RecastPress/actions/runs/41621939824)では、所有JSON wrapperの前に480 BのPHP warningが出て`cgi_complete_json_line`で停止した。要求全体の成功にはしていない。両DBの原JSONを各1,012 source binding・174 Git blob照合付きで保持した。

固定警告分類は`http_response_code()`の出現2、既送信後のheader変更警告1、出力開始・警告元ともbootstrap 135行を示した。PHP内部のwarning_count 0は最終emit前にJSON化された値なので、emit時の警告がない証拠ではない。

[WP・DBなしの8条件](../experiments/php-wasix-cgi-framing-probe/README.ja.md)は、同じ3patch moduleのLinux CIで小／大JSON・buffer有無・header削除有無の全CGI bytesがnativeと一致した。単純な出力サイズやbufferだけでは警告を再現しなかった。

## 固定ソース上の経路

元WPの`status_header()`は`header('HTTP/...', true, $code)`でstatus lineを設定する。固定PHPの`header_remove()`による全削除は通常header listだけが対象で、独立したstatus lineは残る。[head.cのsetter](https://github.com/wasix-org/php/blob/f4bfae79d5c19028349082f707930cf0951d23b9/ext/standard/head.c#L402)は、その状態の`http_response_code()`に警告を出してから処理を続ける。診断wrapperがheader listを空にした後で警告を表示すると、空のCGI header blockが確定し、後続Content-Type設定も警告になる。

[独立したnative比較](../experiments/php-cgi-status-line-probe/README.ja.md)でも、既存status line後の旧setterが同じ2分類の警告を各1件出した。したがってfork固有の不具合とは扱わない。旧setterの完全一致はfalseのまま保持した。

元native比較入口はGETだが、private JSONを渡すため`CONTENT_TYPE=application/json`を設定し、WP実行前に消していなかった。元Wasm入口はGET・body 0で、このheaderを設定していない。固定WPの`wp_is_json_request()`はContent-TypeからJSON要求と判定し、`wp_debug_mode()`はJSON要求で`display_errors=0`にする。source上では、これが元native比較で警告が表示されなかった理由を説明する。警告の非発生やfork間の意味論差とは扱わない。

元native証跡は書き換えない。今回一致したstatus・headers・HTMLと、入口の全request contextが一致することは別であり、private transportのContent-Type／body metadataをWP向けrequest contextへ残さない比較は後続の確認事項とする。

## 修正範囲と受入

所有JSON wrapperだけで次を使う。

```php
header_remove();
header('Content-Type: application/json', true, 200);
```

header APIの第3引数は[SAPIのstatus更新経路](https://github.com/wasix-org/php/blob/f4bfae79d5c19028349082f707930cf0951d23b9/main/SAPI.c#L589)を使う。nativeの既存200→200と404→200は、全CGI 262 Bが期待値に一致し、警告0だった。警告を抑制せず、元WPのstatus/header/body、bufferやJSON化の順序は変更しない。

source-only準備・編集PHP lint・53 unitは通過した。実Wasmの元WordPress要求がCGI framing、全応答のnative比較、DB/session終了、source/module不変、正常清掃をすべて通ることを次のCIで確認する。固定fixtureの修正を任意plugin・全WP互換性や製品runtimeの受入には広げない。

source `7f191b0`の[CI 41626989599](https://github.com/KANIKAMA-Carcinization/RecastPress/actions/runs/41626989599)では両DBで全条件が通過した。警告prefixはなくなり、外側CGIは完全なJSON 1行になった。内側のstatus 200・全3header・HTML 69,399 Bもnativeと完全一致し、元WP・theme・adapterを変更せずに要求全体を受け入れた。各1,039 source binding・178 Git blob照合付きの[成功証拠](../experiments/php-wasix-wp-request-probe/README.ja.md#元テーマ要求の実wasm受入)を保持する。
