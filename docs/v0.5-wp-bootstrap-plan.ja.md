# v0.5の通常WP起動へ進む実装順

2026-11-04。[実装進捗](v0.5-development.ja.md)と[実行ホスト候補](v0.5-runtime-candidate.ja.md)を受けた作業順。既存のv0.5設計を変更せず、P1の標準wpdb接続と通常WP起動に必要な差分を整理する。

## 固定corpusと標準APIの差分

[27ケース](../experiments/php-wasix-wpdb-probe/fixtures/corpus.php)のINSERT・UPDATEは`query()`へSQLを渡す比較であり、`insert()`・`update()`・`delete()`等のヘルパーを比較したものではない。`prepare()`・`get_*()`を上流PHPへ残す方針は維持するが、継承しているだけで互換確認済みとは扱わない。

| 範囲 | 次に比較するもの |
| --- | --- |
| 更新ヘルパー | `insert/replace/update/delete`のformat、NULL、空値、0件更新、公開状態、内部SQLと往復回数。元PHPのschema照会・文字数検査も含める |
| 文字列 | 日本語・4byte UTF-8・quote・backslash・NUL・不正byte。元のASCII限定corpusを保持し、別の通常PHP比較を追加する |
| queryの意味 | 上流の文字列検査・filter・query counter・error後状態。最小adapterで省略した上流処理を、必要箇所から復帰させる |
| metadata | `get_col_info()`のname以外と、元wpdb内部で必要になる型・長さ等。driver固有resultへの直接アクセスの互換化とは分ける |
| DB error | 1064以外、接続失敗、raw message bytes、次操作への状態。driverの公開`String`へのlossy変換をraw互換と呼ばない |
| 接続の寿命 | fresh要求の独立session、未完transactionの切断、close前の失敗。副作用のある要求を自動再送しない |

根拠は固定WP 7.1.3の`class-wpdb.php`と比較用native観測に置く。RustへWPの文字列・SQL生成APIを移植する量を増やさず、接続・結果・errorの境界を補完する。実行profileの上限は測定用の有限値として記録し、16行・16列・4096B等を製品のWP互換上限として確定しない。

更新ヘルパーには[追加ASCII corpus](../experiments/wpdb-crud-probe/README.ja.md)を用意し、MySQL／MariaDBで通常PHPとRust接続の15ケースが一致した。その後[同じcorpusをphp-wasmで実行](../experiments/php-wasix-wpdb-probe/README.ja.md)し、親schema照会を含む公開16 SQL・40 RPC、型・引数・公開状態・counterも両DBのnative基準と一致した。非ASCII・過長／不正入力、通常WP bootstrap等は引き続き残件である。

raw errorについては[保持済みpacketを参照する独立patch](../experiments/wpdb-raw-error-probe/README.ja.md)を先に用意した。実DBとPHP-Wasmの固定ケースまで比較を終え、通常bootstrapの経路への組込みを残す。[固定ケースの実測](../experiments/php-wasix-wpdb-raw-error-probe/README.ja.md)

[通常WPのnative基準](../experiments/wp-bootstrap-probe/README.ja.md)では、両DBで元installer・full wp-settings起動を確認した。通常起動後のautoload対象は115件、最大値は23,778Bだった。現在の固定RPC profileの16行・4KiB/cellや一階層source FSを製品上限へ固定せず、有限のtree探索と全結果のbyte保持・予算を補完する。結果をtruncateしたり入力SQLへLIMITを追加して、通常起動を通過させる方法は使わない。

[有限readonly tree FS](../experiments/wp-source-fs-probe/README.ja.md)は11 unitと元WP全catalogのnative trait検証まで通過した。次に実WASIのdirectory FD・path探索へ接続する。timestampは0固定であり、PHPのfilemtime等のnative一致や全metadata互換まで成立したとは扱わない。

その後の[plain WAT結合](../experiments/wp-source-wasi-probe/README.ja.md)では、Windows上の実WASIで小tree／全WP catalogのdirectory FD・列挙・file read/EOF/closeと変更拒否を確認した。WASIX内部のWindows separator変換をprobe境界へ置き、旧FSは維持した。Linux・PHP実行への組込みとnative metadata互換は引き続き確認する。

[結果collectorの独立実証](../experiments/wpdb-result-budget-probe/README.ja.md)では、合成115行・大きなbinary cellを含むencoded 79,758Bの結果を両DBで全値保持し、予算境界と超過拒否・fresh復帰を確認した。入力SQLの変更・無断truncateは行っていない。現在のcandidate上限を製品値へ確定せず、通常WPの実結果を使う経路へ接続し、driver側packet・全保持量・符号化と同時要求を含めた予算を次に確認する。

## 実装する順序

1. 同じ3patch PHP CGIからprivate file RPC・Rust所有session・両実DBまでの27ケースを成立させる。CGI生bytes、全RPC、元nativeとの比較、正常清掃を一つの実行で確認する。
2. 上表の不足を小さな追加corpusで比較する。既存の比較記録を保存し、raw DB値を結果補正で合わせない。元wpdbが呼ぶschema照会や文字列検査を通せる状態にする。
3. 所有`db.php`を通常の`require_wp_db()`から読み込む最小構成へ接続する。固定archive全体から元WPを配置し、coreはreadonly、RP所有drop-inと設定は専有、要求の一時領域は別能力にする。最初はsingle site、共有cacheなしで通常`wp-settings.php`を通す。`SHORTINIT`だけの成功を通常起動の代用にしない。
4. 元WPで用意した使い捨てDBを二つの比較環境へ同じ初期状態で配置する。固定theme・pluginをPHPのまま実行し、匿名表示、404、ログイン、記事保存・非公開化を順に比較する。認証時刻やnonce等は比較対象を明記し、生応答を保持する。
5. Rust HTTP入口へ完成CGI応答を接続する。要求入力、Host、body、Cookie、response header、出力上限、所有processの期限を明示し、失敗した要求の部分応答を送信しない。既存のbundle配信をWP通常実行の成功として数えない。

DB資格情報はRust側だけに置く。mysqliがPHPへ組み込まれていることと、DBへの到達能力を与えることを分け、driver直接依存・所有drop-in差替え等の衝突拒否を最小構成から確認する。静的な文字列検出だけで任意pluginの安全を証明したとはしない。共有cache・索引・追跡による高速化は、無cacheの基準経路を比較できた後に追加する。

## 通常起動を結合する現在の実装

[php-wasm通常WP検証](../experiments/php-wasix-wp-bootstrap-probe/README.ja.md)を独立した実験として追加する。元3,782file／467dirのcatalogへ所有`wp-content/db.php`一つだけを重ね、元`require_wp_db()`・`wp-settings.php`・`wp_install()`を通す。RustだけがDB資格情報と物理sessionを持ち、PHPへは要求nonce・salt等の専用contextを渡す。install後は同じDBに対してfresh PHP／WASI／DB actorでreadを実行し、既存の通常PHP基準の公開option・posts・autoload集計と比較する。

この経路の候補上限は256行・32列・64KiB/cell・256KiB/raw結果・512KiB/replyとし、元の16列collectorから列数だけを明示的に広げる。元WPのposts全列は23列あるためであり、製品互換上限の確定ではない。SQL生成や文字列検査は上流へ残し、全結果を保持したまま超過時は失敗させる。初回CIでは通常bootstrap完了後のinstallが1,024 RPC上限で停止したため、この経路だけ4,096操作の有限候補へ広げ、他のbyte・時間・結果上限は保持して再検証する。SQL本文・実DB行・password hashは公開artifactへ入れず、操作種別・件数・byte数・digest・固定診断codeを記録する。raw ERRのString変換、全metadata互換、統合時の全資源上限は残件として保持する。

source `5c531b3`の両DB Linux CIでinstall1,323／fresh read162 RPCが完走し、公開19 fieldsが固定native基準と一致した。元source不変・明示close/物理切断・actor終了・EOF・所有containerの正常清掃を確認し、原失敗と成功は別に保存した。次は元テーマのnative CGI基準と同じ匿名要求のWasm描画へ進める。HTTP入口・実plugin・全wpdb・製品資源上限は残件として維持する。

続くsource `7f191b0`では[元テーマの匿名ホーム](../experiments/php-wasix-wp-request-probe/README.ja.md)も両DBで通過した。status200・全3header・HTML69,399 Bがnativeと完全一致し、CGI framing・145 RPC・source/module不変・正常清掃も確認した。所有JSON wrapperのstatus APIに起因した失敗と、private transportのContent-Typeによるnativeの表示条件差は[別報告](v0.5-cgi-status-line-findings.ja.md)へ残す。

[mbstringありのnative31観測・22 SQL](../experiments/wpdb-utf8-probe/README.ja.md)は、source `10eaa68`の[両DB Wasm CI](../experiments/php-wasix-wpdb-utf8-probe/README.ja.md#実wasmでの有効utf-8受入)でも一致した。現行fullWP用actor・RPC・collectorとPHP corpus／adapterを変更せず、各52 RPC・Linux35 unit・178 inputs・正常清掃と、全10比較項目を確認した。OSごとのserver versionだけを固定metadataに基づく期待値へ明示導出し、実結果の変更・文字列の正規化は行わない。固定表はVARBINARYを含むため、text-only table・任意collation・不正UTF-8・上限境界は残件である。

次の比較に向けて、[private file入力と公開要求を分離したnative基準](../experiments/wp-request-context-probe/README.ja.md)を追加した。source `afe8781`の両DBでhome200／404とfresh反復404が通過し、公開contextの3段階一致、JSON要求判定false・display_errors1、全header／HTML・正常清掃を確認した。初回の環境query除去漏れは原判定のまま保持する。[要求context報告](v0.5-request-context-findings.ja.md)に従い、次は同じ有限contextと2応答をWasmへ接続する。既存の成功・失敗証跡とraw error・metadata・session寿命の残件は維持する。

## 進捗の判定

source `3c4dbf1`の[有限な実HTTP結合](../experiments/php-wasix-wp-http-probe/README.ja.md#実http経由の両db受入)も両DBで通過した。Rust HTTPはprivate stdinの設定からfresh workerを管理し、home／404／反復404の完成応答だけを公開する。実socketの全本文・origin fields・EOF、固定7不正要求の事前拒否、worker／server回収と所有DBの正常清掃を確認し、各2,711 source bindings・215 Git sourcesを照合した。上の順序5における固定匿名要求の独立実証であり、順序4の認証・書込み・任意pluginの完了ではない。

次は既存の受入済みworkerを保ったまま、新しいworkerで「完了済み応答＋限定診断」のprivate IPCを抽出する。全応答のnative比較は検証adapter側へ残す。単に固定期待値の検査を削除せず、未知のHTML・header・contextの公開契約と製品HTTP接続を後続で確認する。共有cacheやcompile再利用は、この経路との等価性を比較できる形で追加する。

応答codecの抽出はsource `18059d9`で先に成立した。[独立library](../experiments/wp-private-response-probe/README.ja.md)はWindows／Linuxの16 unit、保存済み応答12件とprivate診断3件で形式・予算・生bytes保持を検証した。デコード成功は実行完了や公開許可を意味しない。次はこのlibraryを新しい独立workerのprivate応答経路へ組み込み、元installer／readと匿名home／404／反復404を実PHP-Wasm・両DBで再通過させる。旧workerと旧HTTPの受入済み結果は維持する。

その[独立workerの実行](../experiments/php-wasix-wp-private-worker-probe/README.ja.md#実php-wasmでの両db受入)はsource `209090a`の両DB CIで通過した。元installer／read・home／404／反復404、全応答と3 snapshot、59 unit／219 inputs・正常終了を確認した。workerのWP native比較はなく、controllerだけで比較し、元private stdoutは公開せず検証済み項目を選ぶ。次は独立HTTP adapterがこのworkerを監督し、サービス実行側でnative応答ファイルを読まずに完成応答を返す有限profileを比較する。受付条件に基づく公開許可と診断の範囲はHTTP側で明示し、任意要求や製品CLIの完了とは分ける。

各段階は入力版・実行結果・失敗・清掃の証跡を揃えて判定する。固定27ケースの成立、標準wpdb APIの成立、通常WP起動、HTTPからのtheme/plugin実行、製品採用は別の到達点とする。元設計のP1全体やP0の残件を、この順序表だけで完了へ変更しない。

source `25f93d7`では[サービス側のnative比較を外した実HTTP](../experiments/php-wasix-wp-private-http-probe/README.ja.md#比較を分離した実httpの両db受入)も両DBで通過した。元installer／read、実HTTPのhome／404／反復404と拒否7種、全3 worker／serverの回収・DB正常清掃、12 unit／232 inputsと元sourceへの照合を確認した。公開許可はHTTP受付条件から導き、workerの公開許可flagを変更しない。nativeとの全応答比較はcontrollerへ残し、サービスの記録は閉じたsummaryに限定する。

次は1所有worker内でのcompile1回・fresh要求3回を独立実証する。Engine／Moduleだけを共有し、WASI／PHP状態・SourceFs／private context・actor／RPC／access／captureを要求ごとに新設する。private入力は上限付きJSONLと要求番号へ分け、同一PIDでcaptureが衝突しない名前、初回compileと各要求の期限、失敗後のセッション終了を確認する。shared PHP状態やDB接続、応答cache、HTTP poolの追加はこの最小段階には含めない。

この[compile再利用の実証](../experiments/php-wasix-wp-session-probe/README.ja.md#compile1回fresh要求3回の両db受入)はsource `5dc3519`の両DB CIで通過した。同一所有PIDでcompile1回・要求内compile0回・3要求の全応答とcontextが一致し、64 unit／241 inputs、48 controller checksと親監督mock3件、各3,575 source bindings・254 Git sourcesを確認した。別sessionの不正初回番号／早期EOFはguest0件で拒否し、全session回収と所有DB正常清掃も成立した。元ACKはprivateのまま、検証済みprojectionとサイズ／SHAだけを保存する。

次は独立した有限HTTP adapterへこのsessionを接続する。最初は所有worker1件・同時実行1件・固定3要求とし、READY後の受付、要求番号と応答の対応、HTTP側の公開許可、正常EOF／最終summary／reapまでを監督する。要求失敗やprotocol違反が起きたsessionを再利用せず、HTTP切断後も所有権と期限を保持する。home／404／反復404の全HTTP応答と既存の事前拒否条件を両DBで再比較し、pool・応答cache・任意要求や製品CLIへの接続は後続とする。

source `d558a23`の接続は両DBで成功した。READY後に受け付けたhome／404／反復404が全応答・公開contextともnative基準に一致し、不正要求7件は400で拒否した。1 worker・compile1回・要求内compile0回、3件目の応答前のEOF／最終summary／reap、アダプターと所有DBの正常終了を確認した。HTTP側が応答待ちを手放す場合の監督と回収は所有mockで検証した。[実HTTP受入記録](../experiments/php-wasix-wp-session-http-probe/README.ja.md#両dbの実http受入)

次は、この有限profileのまま起動時の入力配置をリポジトリから分離する。親とworkerが同じリリースを検証し、別ディレクトリへ移した配置から起動して同じ応答を得る。欠落・差し替え・別版の混在・配置外参照は待受前に拒否する。[配布用配置の実装順](v0.5-runtime-candidate.ja.md#配置を分離する次の実装)

配置分離はsource `7c51b92`のLinux CIで受け入れた。移動した配置を実験用CLIから起動し、両DBで固定3要求の全応答・要求コンテキスト、事前拒否7件、1 worker・compile1回、正常終了を確認した。[実起動の証跡](../evidence/wordpress-preview-release/ci-42488374173/provenance.json)

プラグインについては、所有DBで標準API候補をWordPress標準の `activate_plugin()` から有効化し、通常ローダーが読むことを確認した。DB／キャッシュの所有drop-inに衝突する候補は全体を拒否し、設定で選ぶDB接続処理の疑いが解消しない候補は保留してローカルのRP開発者向け報告を生成した。次は固定の標準API候補をprivateなPHP-Wasm実行とRust DBへ接続し、有効化・新規要求・所有プロセスの終了を比較する。[プラグイン試験と通常PHPの両DB基準](../experiments/wp-plugin-admission-probe/README.ja.md)

PHP-Wasmでの固定プラグイン試験は両DBで通過した。privateな有効化と3描画を別processで実行し、独立SQLでの有効化状態、通常PHPと同じ応答・要求コンテキスト、4 processと所有DBの正常終了を確認した。次のキャッシュ試験では、通常PHPで通過した固定2グループのRustストアをWasm内からprivateチャネルで呼ぶ。[PHP-Wasm試験](../experiments/php-wasix-wp-plugin-admission-probe/README.ja.md)・[Rust要求内キャッシュの基準](../experiments/wp-object-cache-rust-probe/README.ja.md)

固定2グループのキャッシュは実PHP-Wasmでも通過した。compile1回・新規WASI要求2件で、通常PHPの56観測と一致した。各32操作後の予約解放とprivateチャネルcloseを確認した。DB側では、両DBの実ERRをPHP-Wasmの標準wpdbとRust actorへ通し、7 SQLの返り値・状態・結果と3 ERR本文が通常PHPおよびwireの観測と一致した。[Wasmキャッシュ](../experiments/php-wasix-wp-object-cache-probe/README.ja.md)・[実ERRのPHP-Wasm比較](../experiments/php-wasix-wpdb-raw-error-probe/README.ja.md)

標準ローダーでRust drop-inを読み込むと、固定操作は一致する一方で外部キャッシュフラグが有効になった。遅延フック登録だけの管理下shimでは、PHP-Wasmの通常bootstrapでも標準キャッシュとフラグを維持できた。固定2グループの9操作をRustへ渡してから、標準キャッシュを同じインスタンスに戻した。標準オプション、公開応答、初期応答を除くDB RPCを基準実行と比較し、両DBで一致した。共有層の接続は別に検証する。[ローダー比較](../experiments/wp-object-cache-dropin-probe/README.ja.md)・[通常起動との結合](../experiments/php-wasix-wp-cache-bootstrap-probe/README.ja.md)

共有層の最初の再開試験は、同じDBが稼働し、検証済みのコミット座標とログが残る条件に絞る。切断中に別接続でコミットし、確定済み座標から再生して独立したSQL読み取りと一致するまで共有ヒットと格納を停止する。再開時は空の新世代を使い、旧チケットを引き続き拒否する。

固定1行の読み取りで、Rust側がヒット、SQL読取りと格納、監視停止時のSQL直読を切り替えることを両DBで確認した。PHP-Wasmの最初の共有読取りは行ロックで値を固定した。続く両DB試験では行ロックを外し、要求間で実binlogのコミットを有限に再生した。初回と3回目にSQLで旧値と更新値を取得し、2回目は共有ヒットした。3回とも標準オブジェクトキャッシュと応答を維持した。[DB連動の実測](../experiments/binlog-shared-cache-probe/README.ja.md)・[PHP-Wasmとの結合](../experiments/php-wasix-binlog-dependency-probe/README.ja.md)

確定済みの座標を使えない場合は、バックエンド別のスナップショットから組み直す。MariaDBはスナップショットと同じセッションで得る座標、MySQLはGTID付きの重複再生が候補となる。MySQLでは、先に開いたスナップショットから旧値が見える間にも、後続のグローバルbinlog座標を取得できることを既存試験で確認している。[両DBのスナップショット試験](../experiments/binlog-probe/README.md)

標準WPでの最初の適用候補は `wp_load_alloptions()` が発行する固定プロファイルのSELECTとする。既存のLinux証跡では、両DBで各要求の10番目に1回現れ、ホームは115行・2列、後続の2要求は各117行・2列だった。初回ホームの前後で対象行数も変わったため、基準と試験は標準経路で準備した後の同じDB状態から比較する。Rust側で対象SQLとセッションを厳密に識別し、行順、値のバイト、列メタデータ、標準PHPの応答、後続SQLが参照するセッション状態を照合する。適用条件に合わない要求は通常のDB経路へ渡す。効果はDBへの実行回数と取得量で測る。[MySQLの要求証跡](../experiments/php-wasix-wp-private-worker-probe/evidence/ci-41771428584-mysql/raw/experiments/php-wasix-wp-private-worker-probe/evidence/linux-mysql.json)・[MariaDBの要求証跡](../experiments/php-wasix-wp-private-worker-probe/evidence/ci-41771428584-mariadb/raw/experiments/php-wasix-wp-private-worker-probe/evidence/linux-mariadb.json)

読み取りロックを使う最初のautoload試験では、標準SQLの結果を保持し、準備済み404の2要求でDB実行1回と共有ヒット1回を両DBで確認した。続くLinux試験では、実際の `rp_options` の固定オプション更新を両DBで観測した。コミット後に標準SELECTを再実行し、対象結果の変更と他のRPC・ページ応答の一致を確認した。[標準autoloadの共有](../experiments/php-wasix-autoload-cache-probe/README.ja.md)・[実コミットとの結合試験](../experiments/php-wasix-autoload-binlog-probe/README.ja.md)

要求前に同じログで位置の前進を検出した場合も、両DBで共有結果を破棄してから、同じ標準SELECTを通常のDB経路で実行できた。独立接続で更新を確認し、追加ヒットと再格納が0件、予約が0バイト、通常PHPの404応答が一致した。キャッシュを使った要求で応答確定前の再照合に失敗した場合は、その応答を破棄する。監視接続の切断と再同期はそれぞれ別の受入条件とする。[通常DB経路の比較](../experiments/php-wasix-autoload-bypass-probe/README.ja.md)

共有をプレビューへ組み込む前に、同じ要求列をキャッシュなしと比較し、通常のDB actorと監視接続を分けて実SQL数・取得バイト数・要求時間を測る。失効試験の正常経路をソースから数えると、監視コードが明示的に発行するSQLはMySQLで43回、MariaDBで34回になる。内訳は監視開始1回、位置の据え置き確認5回、コミットの有限再生1回に伴う照会である。標準SELECTの省略は1回なので、プレビューへの組込みは監視の費用も含む比較で判断する。

4要求の公開証跡では、WordPressの `query` RPCは両DBとも50・28・28・28回だった。共有ヒット1回を引くとactorのSQLは133回になる。監視コードの明示的なSQLを加えた試験経路の見積もりはMySQLで176回、MariaDBで167回となる。次の候補では、ソースの照合を監視接続の開始・復旧時にまとめる。要求時に接続先DBから取得した位置まで同じソースの変更を適用できた場合に共有を許可し、照合できない要求は通常のDB経路を使う。[失効試験の証跡](../experiments/php-wasix-autoload-binlog-probe/README.ja.md#両dbの実測)

Windowsの両DBでは、この候補を固定テーブルで実行した。ライブ監視の適用位置と同一ログの現在位置を照合し、読み取り4回で位置確認4回、通常SELECT 2回だった。共有ヒット2回のうち、1回は実コミットの適用後に取得した新値で、監視の遅れと切断を観測した場合は通常SELECTで新値を取得した。次は監視接続と別に作るPHP-Wasm用のDB接続が同じソースを参照することを確認し、並行書き込みがある場合の再格納条件と費用を比較する。[ライブ監視の固定試験](../experiments/binlog-autoload-frontier-probe/README.ja.md)

別接続の同一性は、両DBのネイティブ試験で先に確認した。別アカウントの2接続が同じ所有DBの公開識別子を読んだ場合に共有を許可した。異なる識別子の試験行を読み取った場合は共有を拒否し、読み取り接続には監視用nonceの参照権限を与えずに成立した。PHP-Wasmのactorとライブ監視を同じ要求で結ぶ試験が次の境界となる。[接続の同一性試験](../experiments/binlog-source-identity-probe/README.ja.md)
