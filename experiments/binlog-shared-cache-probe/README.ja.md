# 実DBのコミット観測による共有キャッシュ失効

Rustの共有キャッシュ候補を、所有するWindows上のMySQL 8.4.13とMariaDB 11.8.9で検証する。対象はInnoDBの固定1行を読むキャッシュキー1件で、値の論理予算は64バイト。DBは接続元とデータディレクトリを検証した使い捨てインスタンスを使う。MySQLは証明書と接続先名を検証したTLS、MariaDBはfixtureのループバック接続を使う。

別接続の未コミット更新が外から見えないことを確認し、ROLLBACK後に値・binlog座標・キャッシュ世代が維持されることを比較する。次の更新をCOMMITした後、同じ開始座標から有限binlogを再生する。CRC32と行の前後像を照合し、XIDを処理するまでは旧値のヒットを維持する。コミット済みバッチの適用時にエントリーと予算を解放し、旧世代で取得した値の再格納を拒否する。新世代でDBを読み直してヒットを確認する。ソースのEOF後は共有ヒットと格納を停止し、残予算はゼロになる。

続いて同じコミット座標にライブ監視を接続し、キャッシュを作り直す。別接続から、所有DB上で同じアカウントの専用binlog接続と確認したIDだけを切断する。監視側が接続喪失を受け取ると共有ヒットと格納を止め、旧チケットを拒否し、予約を解放する。DBの値は別接続から引き続き読める。

切断中に別のwriterが1件を更新し、独立したSQL接続でコミットの前後を確認する。保持した座標から別のライブ接続で完全な更新とXIDを再生し、検証済みの終端まで到達してから空の新世代を開く。旧チケットの格納を拒否し、SQLで読み直した値を新チケットで格納してヒットを確認する。再開した監視を再度切断し、共有アクセスの停止と予約解放も確認する。

固定行の読み取りではRust側がSQLを所有する。初回格納、別接続からのヒット、監視停止中のDB直読、復旧後の初回格納、再ヒットの順に、依存行のSQL実行回数は両DBとも `1, 0, 1, 1, 0` だった。監視停止中は新しいDB値を読み、共有層には格納しない。

この試験で確認する整合性は、単一プロセスが対象のコミットまたは監視切断を観測した後のもの。復旧条件は、同じDBが稼働し、確定済み座標と同じbinlogファイルが残る固定ケースに限る。継続監視での遅延上限、ログ消失・ローテーション・DB再起動後の再同期、任意のWordPressキーとDB行の対応付け、PHP-Wasmへの共有層の接続は別途検証する。

## 再現

既存のWindows DB fixture用のツールを用意してから、リポジトリルートで実行する。既存binlogソースとロックファイルは固定コミットから専用ディレクトリに派生し、既存の検証コードや記録を直接更新しない。

```powershell
python -B experiments/binlog-shared-cache-probe/windows_check.py --backend mysql
python -B experiments/binlog-shared-cache-probe/windows_check.py --backend mariadb
```

両DBで最初のコミット1件に加え、切断中のコミット1件の再生と復旧を確認した。DBは正常終了した。実行記録は [MySQL](evidence/windows-mysql.json) と [MariaDB](evidence/windows-mariadb.json) を参照。
