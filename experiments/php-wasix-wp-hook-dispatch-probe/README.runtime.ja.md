# 実PHP-WASIX hook dispatch PoC

この専用workspaceは、固定PHP-WASIX 8.5.12とWordPress 7.1.3のsource-bound overlayを使い、実際の `apply_filters()` と `do_action()` から選択された `WP_Hook` callback tableをRust `Dispatcher` にimportして実行する。既存の7 profile PHP compatibility bridgeやそのreceiptは変更しない。

PHPはcallable自体をtransportへ出さず、request-scoped `HandleRegistry` のdescriptorだけを渡す。Rust側は元のcallback UID、priority、insertion order、accepted args、handle identityを検証する。各PHP callback直前にWP_Hookのprivate current priorityをmethod内closureから同期する。filterの戻り値はchainへ戻し、action callbackの戻り値は捨てる。`all` callback、`$wp_actions` counter、`$wp_current_filter` stackはWordPressの元 `plugin.php` が先に処理し、Rustには選択された名前付きhookだけを渡す。

完了時はWP_Hook iterationを正常終了させ、callback tableを前後比較する。Rust dispatcherからregistration leaseを解放し、PHP registryのhandle release ACKを受け取ってからrequest registryをcloseする。filter fixtureはcallback順、引数、priority、`current_filter()`、`doing_filter()`、`did_filter()`、filter結果を検証する。action fixtureは`all`の実行順、accepted args、`current_action()`、`doing_action()`、`did_action()`、WP_Hookのaction state、無視される戻り値と最終cleanupを検証する。引数なしactionではWordPress標準loopの空文字placeholderと`all`側の引数形も確認する。通常actionでは、2引数を渡して`accepted_args=5`で登録したcallbackにも、実際に渡された2引数だけが届くことを固定WordPress native oracleと照合する。

## 実行

```sh
python3 scripts/wordpress_reference.py fetch
# 固定Upstream Actions artifactをworkflow内で取得・照合する。
python3 experiments/php-wasix-wp-hook-dispatch-probe/check_overlay.py
python3 experiments/php-wasix-wp-hook-dispatch-probe/check.py
```

`check.py` is Linux-only and uses Rust 1.94.0, Wasmer 7.2.0 Cranelift, and Wasmer-WASIX 0.702.0. GitHub Actions runs on Ubuntu 24.04, verifies the fixed PHP artifact ZIP and extracted Wasm size/hash, and sends its token only to the pinned `api.github.com/repos/wasix-org/php/actions/artifacts/12371010145/zip` endpoint. Its fourteen runner scenarios are `filter`, `ref-array`, `action`, `action-ref-array`, `action-ref-array-empty-bucket`, `action-ref-array-empty-bucket-reinsert`, `action-ref-array-empty-bucket-add-action`, `action-ref-array-global-replace`, `action-throwable`, `action-nested`, `action-mutation`, `action-removal`, `action-remove-all`, and `action-deferred-add`. The current Windows-local source-validation receipts do not represent completed guest runs.

Cranelift stays at no optimization to match the existing real PHP bridge. The Rust host reports artifact read, module compile, guest start, and first bridge-frame wait to stderr. The checker runs fourteen scenarios separately (filter, ref-array, action, action-ref-array, action-ref-array-empty-bucket, action-ref-array-empty-bucket-reinsert, action-ref-array-empty-bucket-add-action, action-ref-array-global-replace, action-throwable, action-nested, action-mutation, action-removal, action-remove-all, action-deferred-add), with a 300-second limit per runner. On timeout it records bounded stdout/stderr tails and their byte counts and SHA-256 digests.

Windows上で同じrunnerを動かすとCranelift 0.133.0のlowering panicが起きるため、Windowsのcargo checkやPHP lintを実PHP-Wasm実行の証明とは扱わない。WSLはこのworkflowの実行環境ではない。

## 実行中アクションへのcallback追加

`action-mutation` adds a priority-15 callback from a priority-5 callback and checks `mutator -> added -> tail`. `action-removal` removes the sole pending priority-15 callback during dispatch and checks `mutator -> tail`. `action-deferred-add` adds a callback at the active priority 5. The callback is absent from the first pass (`all -> mutator -> peer -> tail`) and runs during the second `do_action()` in the same PHP request (`all -> mutator -> peer -> added -> tail`). The fixture checks `did_action()` values 1 and 2, reset hook state after the request, the final four-row callback table, native WordPress oracle equality, release acknowledgements, and zero live handles at request close.

## Bounded direct edit of `WP_Hook::$callbacks`

The current `action-ref-array` source directly inserts a new priority-8 entry into the public `$hook->callbacks` bucket and unsets the previously registered pending entry. The bucket retains only the new UID, while the private priority list stays `[1,2,5,8,10]`; WordPress invokes the new callback at priority 8 and continues to priority 10. PHP's native WordPress 7.1.3 oracle, fixture lint, Rust formatting, offline host build, and focused dispatcher contract test pass; see the [local source-validation receipt](evidence/windows-direct-callback-table-replacement-validation.json). The Rust contract test confirms the removed callback handle is yielded for release after mutator resume and before the directly inserted callback runs. The PHP bridge uses the existing add notification/ACK followed by removal notification and PHP handle-release acknowledgements. A Windows runner attempt reads the pinned artifact but Cranelift panics in `module_compile_start` before guest start; bounded output is recorded in the receipt. There is no successful PHP-WASIX run or CI evidence for this source. Run 44488505287 predates this direct public-table change and does not prove it.

The separate [direct priority-bucket unset oracle](evidence/windows-action-ref-array-unset-bucket-validation.json) records a negative WordPress behavior boundary. Unsetting the whole future `$hook->callbacks[8]` bucket while priority 5 is running leaves private `priorities` containing 8. WordPress skips the removed callback and reaches priority 10, but emits `Undefined array key 8` and `foreach() argument must be of type array|object, null given`. The oracle temporarily installs an error handler that records and suppresses those warnings so it can observe the later callback; an application error handler that promotes warnings to exceptions may abort dispatch instead. The Rust contract test covers removal-handle release ACK before the next PHP priority callback; it does not exercise this direct PHP edit through the bridge. This is native WordPress plus host contract evidence only; no PHP-WASIX run or CI evidence is claimed.

The new `action-ref-array-empty-bucket` mode directly assigns `[]` to the scheduled priority-8 bucket, then sends the existing callback-removal notification and waits for its ACK before resuming the Rust dispatcher. The pinned native oracle confirms the bucket remains present and empty, priority 8 remains in the private schedule, no warning is emitted, the removed callback is skipped, and priority 10 receives the mutations from priority 5. Its native output is recorded in [the validation receipt](evidence/windows-action-ref-array-empty-bucket-validation.json). The Linux `check.py` matrix now includes this mode. Local PHP lint, oracle, Rust host compile, and 66 dispatcher contract tests pass; the Windows guest attempt still panics in Cranelift during module compilation before guest start, recorded in [the attempt log](evidence/windows-action-ref-array-empty-bucket-attempt.log). No PHP-WASIX guest success is claimed.

An isolated Windows trial built the same runner with Wasmer 7.2.0 Singlepass selected instead of Cranelift. The pinned PHP-WASIX 8.5.12 module was rejected at `module_compile_start` with `exceptions proposal not enabled (at offset 0xa044)`; the guest never started.
